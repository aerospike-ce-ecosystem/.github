# Contributing

This guide applies to every repository in the
[aerospike-ce-ecosystem](https://github.com/aerospike-ce-ecosystem) organisation.
It is stored in the org-level `.github` repository, so any repository that does
not publish its own `CONTRIBUTING.md` inherits this one. Where a repository has
its own guide, that one wins — it will have the build commands that actually
apply.

By participating you agree to the [Code of Conduct](./CODE_OF_CONDUCT.md).

**Found a security vulnerability? Stop and read [SECURITY.md](./SECURITY.md)
instead.** Do not open a public issue.

## Reporting a bug

Use the issue templates. They ask for the product version and environment
because without them a report usually cannot be reproduced, and version drift
between components is a recurring cause of problems here.

If the problem spans more than one repository — say an `aerospike-py` API change
that breaks the Cluster Manager backend — file it in **project-hub** with the
`cross-repo` label rather than filing the same thing several times.

The `bug-reporter` skill in the plugins repository can help assemble a report if
you are already using Claude Code, but it is a convenience, not a requirement.
A hand-written issue is equally welcome.

## Setting up

For a single repository, clone it and follow its own README — each one is
independently usable.

For cross-repo work, `workspace` gets you everything at once:

```bash
git clone --recursive https://github.com/aerospike-ce-ecosystem/workspace.git
cd workspace
make doctor   # checks for uv, podman, kind, rust, go, node, pre-commit
make init     # initialise all submodules
make help     # every available target
```

Useful targets once that is done — `make build-py`, `make build-acko`,
`make build-cm`, `make build-ackoctl`, `make test-all`, `make lint-all`,
`make start-aerospike`, `make dev`.

Run each repository's own tests and linters before opening a PR. The
per-repository README or `CLAUDE.md` documents the exact commands; `make help`
in `workspace` lists the aggregated equivalents.

## Making a change

1. **Open an issue first** for anything beyond a typo. It is cheaper to discuss
   an approach than to review the wrong implementation.
2. **Branch from `main`.** Nobody pushes to `main` directly.
3. **Keep the PR to one concern.** A PR that fixes a bug and reformats 400
   lines is two PRs.
4. **Write tests** for behaviour changes, in whatever the repository already
   uses.
5. **Open the PR** describing what changed and how you verified it. Paste the
   command output; "tests pass" is not evidence.

### Commit messages

[Conventional Commits](https://www.conventionalcommits.org/). This is enforced —
`workspace/.commitlintrc.yaml` restricts the type to:

```
feat  fix  refactor  docs  chore  style  test
```

```
feat(batch): add retry option to batch_write
fix(webhook): reject namespace count above the CE limit
docs(adr): record the decision to drop label-triggered automation
```

The daily release workflows read these: `feat` bumps a minor, everything else
bumps a patch, and `BREAKING CHANGE` in the body bumps a major. A sloppy type
produces a wrong version number, so it is worth a moment's thought.

### Architecture decisions

Anything that changes an interface between projects, adds a dependency, or
would be expensive to reverse should get an ADR before the code. Open an
`ADR Proposal` issue in
[project-hub](https://github.com/aerospike-ce-ecosystem/project-hub/issues/new/choose).
Existing ADRs are the
[ADR index](https://aerospike-ce-ecosystem.github.io/project-hub/docs/architecture/adr-index);
reading a few is the fastest way to see the expected shape.

### Cross-repo changes

The ecosystem has a dependency chain, and changes propagate along it:

```
aerospike-py → ACKO → cluster-manager → plugins
```

Merge in that order. A breaking change in `aerospike-py` lands first;
downstream repositories adapt afterwards. Merging downstream first produces a
release pairing nobody has tested.

Track the whole piece of work as one issue in `project-hub` with the
`cross-repo` label, linking the per-repository issues as
`aerospike-ce-ecosystem/<repo>#<number>`.

## Community Edition constraints

These tools target Aerospike **Community Edition**, which is materially more
limited than Enterprise. Contributions must respect that:

- **Maximum 8 nodes** per cluster
- **Maximum 2 namespaces**
- **No XDR**, no TLS, no rack-aware replication, no enterprise security
- **No LDAP/OIDC in the server** — authentication in Cluster Manager sits above
  Aerospike, not inside it

ACKO's admission webhook enforces the first three. A PR that removes those
checks to make an Enterprise feature work will be declined — the constraint is
the point.

## Review

- Every change goes through pull request review. Nobody merges their own work
  unreviewed.
- Reviewers look at correctness, tests, and whether the change fits the
  project's stated goals.
- Address feedback with commits on the same branch rather than a force-push, so
  reviewers can see what changed.
- Reviews are about the code. See the [Code of Conduct](./CODE_OF_CONDUCT.md).

## Licence

Unless a repository states otherwise, contributions are licensed under
**Apache-2.0**, matching the repository you are contributing to. Check the
`LICENSE` file — a small number of repositories differ, and a few do not yet
declare one. If the repository you are working in has no `LICENSE`, please ask
before contributing anything substantial.
